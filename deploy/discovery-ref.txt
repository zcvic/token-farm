# ---- 2026-11 第三批：35a8d552 → 763ed2f510（1 个提交，取 3 项、有意不跟 3 项）
#      本批是参考仓的一次生产事故复盘（SOCKS5 代理随机出口被上游 403、隧道
#      超时约 50%，两类失败都被记在当时在飞的 Key 上，800 把 Key 三连失败后

#      已取（按能力重写，不引入参考仓的 keypool/relay 结构）：
#        · 链路失败不归因到 Key：`client._network_error` 仍标 `network_error`；
#          `adapter._cool_down` 对 `network_error` 直接返回 False——即使运维把
#          `cooldown_5xx` 打开，DNS/超时/代理断开也不冻号。`_chat_accounts` 遇到
#          network_error 改为**换下一个账号继续**（不冷却）：每个账号可以走不同
#          代理，换号仍有意义；全部失败才抛出最后一个错误。
#        · Cluster TPM 429 是账户级上限：`client._response_error` 在 429 且文案含
#          `Cluster TPM` / `cluster rate limit` 时标记 `cluster_rate_limited`
#          （保留 retry-after），而不是普通的 `rate_limited`。适配器不冷却、不
#          轮换账号，而是按 retry-after 等共享窗口（每次 ≤15s、每请求最多 2 次），
#          然后把**同一个账号**放回队首重试；超过预算才把 429 交给客户端。
#          冷却单个账号只会把整池轮着冻一遍，而 ceiling 在所有 Key 之上。
#        · 模型下线提示：上游返回 404 `error.code=model_disabled` 且带
#          `suggested_model` 时，`_response_error` 保留 404 与稳定 code，并把
#          「上游建议改用 X；不会自动改写请求」写进错误文案。
#      有意不跟：
#        · `model_disabled` 的**静默改写 + 自动重试**：参考仓为了旧客户端配置
#          能用，直接把请求体 model 换成 suggested_model 再打一次。本仓在
#          `docs`/适配器里明确不做 force-model 静默改写——客户端要 A 回来 B 无法
#          解释，且 suggested_model 未必在本仓目录里（还有 `discovery/` 前缀和
#          别名映射）。只透出建议，由用户/客户端决定。
#        · 池级 `ReviveStaleLinkRests` / `ProbeRound` / `NoteProbeSuccess` 与
#          「连续 8 次失败才 rest 一个 Key」：本仓探针是人工触发的

#          有显式入口（`clear_account_cooling`）。照搬会多出一套没人驱动的池级
#          修复逻辑。参考仓需要它，是因为旧版本把链路错误写进了 Key 的冷却，
#          本仓这次改完源头后没有需要修复的历史状态。
